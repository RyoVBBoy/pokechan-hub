### A-2. 入れかえ案は3か所以上で別々に作られている

同じパーティに対して、入れかえを出す所が少なくとも5つあり、**それぞれ候補の集め方・評価・判定が違う**。

| 場所 | 候補の集め方 | 評価 | 採用の条件 |
|---|---|---|---|
| ① 相性のいい仲間（`prSwaps`） | 図鑑の全264匹（メガの姿は除く） | `prScore`（タイプの受け合い中心の点）＋苦手な相手への1対1（`estHit`） | 点が0.5以上良くなる → 上位8案を `dgTeam0` で計算し直し、×と△以下が増えず、◎○が△以下に落ちない上位4案 |
| ② チェックのタイプの重なり（`partyCheck` の `swaps`） | そのタイプを半減以下で受けられる匹を合計種族値の高い順に4匹 | タイプだけ | **計算し直さない** |
| ③ チェックの後出し不足（`dgDefSwaps`） | 使用率の上位40＋種族値上位60・メガ20 | 後出しできない相手に `swIn==='win'` になる数 | `dgTeam0` で計算し直して、後出しできない相手が減り、×・△以下・一撃で半分以上が増えない |
| ④ 改善案（`dgImprove` の swap） | ③と同じ集め方 | 問題の相手に対する `r>=4` 1点＋後出し0.6点 が1.5以上 | `impJudge`（重み `IMP_W` の合計が0.5より大きく、×が増えず、◎○が△以下に落ちない） |
| ⑤ 敗因の診断（`loseReasons` の②） | 「だれも答えられない相手」を答えられる匹 | `dgTeam` の× | `dgTeam0` で計算し直して×が減る |

→ **[コード] 同じパーティ・同じ候補でも、①ではおすすめ、②では出ない、④では「悪くなる」として外される、ということが仕組み上起こる。** どれが正しいかを決める共通の基準がない。

### A-3. 候補が評価されるまでの流れ（①「相性のいい仲間」の場合）

1. **候補のもと**：`prRank(mem)` の `pool = P.filter(c=>!have.has(c.no)&&!have.has(c.base))`。図鑑の全264匹から、パーティと同じ種類（元の姿で比べる）を除く。**メガシンカの姿は P に入っていない**ので、候補はいつも元の姿（[確認] `P.filter(p=>p.base).length===0`）。
2. **使うデータ**：候補は**種族値・タイプ・覚えられる技（`LSD`）・持てる特性すべて（`ABD`）**。パーティの匹は `prMon`（メガストーンを持っていればメガの姿）。
3. **計算**：`prScore`（A-4）→ 合計点で並べる → 上位40匹だけ `prThreatCheck`（苦手な相手への1対1）を足す → もう一度並べる。
4. **外される条件**：同じ種類がパーティにいる。入れかえ（6匹そろったとき）では軸（`axis`）の匹は外さない。`prSwaps` は「点が0.5以上良くなる」「入れかえ後の計算で×・△以下が増えない、◎○が△以下に落ちない」。
5. **点数**：`prSum = Σ R.pts + (合計種族値−500)/60`。
6. **並べ方**：点の高い順。入れる匹が重なる案は良い方だけ、上位8案 → 計算し直して4案まで。
7. **画面**：候補ごとに点の大きい理由を3〜4つ（`k!=='bad'` で文のあるもの）と注意（bad）。6匹そろったときは「計算」の札に変更前→変更後の数。
8. **説明と中身が合っているか**：A-6 と B-3 を参照（合っていない所がある）。

## B. 今の問題

### B-1. 実装の誤り（確かめたもの）

1. **[確認] 診断でメガシンカ2匹を同時に数えている。** `dgTeam0` は1匹ずつ `mkMon` するので、メガストーンを持つ匹は全員メガの姿で計算される。1試合でメガシンカできるのは1匹（[未確認] 公式で確認していないが、複数の資料が一致）。
   手順：リザードン（リザードナイトY）・ガブリアス（ガブリアスナイト）・ドドゲザン・ガオガエン・ゴリランダー・ブリジュラスで `dgTeam0(…,20)`。
   結果：`T.M` はメガリザードンY・メガガブリアスで計算。ヌメルゴン（ヒスイ）・ウルガモス・サーフゴーの3匹は「◎（2匹以上で安定）」だが、**その2匹がちょうどメガの2匹**（同時には出られない）。
   影響：パーティの ◎ の数・相手ごとの対応力・総合のまとめ・改善案の比べ方（`dgMetric` の st）・相性のいい仲間の入れかえの確かめ。`dgSelect` は選出でメガを1匹にしているが、パーティ全体の段階 `r.lvl` を使う所（`lost`＝選ばなかった匹に頼る相手）にはこの影響が残る。
2. **[コード] 入れかえ案（①）は、メガストーンを持つ匹を外す案も出すが、外したあとのメガシンカの数を見ていない。** `prSwaps` は軸以外の全員を外してみる。候補は元の姿（メガストーンなし）で評価・追加されるので、メガシンカできる匹が0になる案も、それを知らせずに出しうる。
3. **[コード] △の段階に「受けて有利（wall, r=3）」が含まれる。** `lvl` の式は r≥4 だけを「安定」に数え、r=3 は r=2（不安定）と同じ2になる。DG_LV の説明「△＝対応が不安定（乱数・同速・条件しだい）」と合わない。
4. **[コード] 見出し「理由の多い順」と実際の並び（点の順）が違う**（A-6）。

### B-2. 前提の置き方が違う（同じ候補を別の条件で比べている）

- **[コード] 候補は元の姿・パーティはメガの姿。** `prScore` の候補 `c` は `P` の元の姿で、メガストーンを持たせた形では評価しない。パーティの匹は `prMon` でメガの姿。メガシンカで強くなる候補の価値が見えない。
- **[コード] 候補は「覚えられる技」「持てる特性すべて」、パーティは登録した育成。** 交代技・場づくり・積み・天気の点は、実際の型（`detSet`）に入っていなくても付く。
- **[確認] 例：** 上のパーティで `prSwaps` の1位は「ゴリランダー → エルフーン」（点の差21.67、うち88%がタイプの受け合い）。評価に使った型は「いたずらごころ・ムーンフォース・エナジーボール・サイコキネシス・まもる・持ち物なし」（集計なしの自動の型）。エルフーンが対戦で担う役（おいかぜ・アンコール等の補助）は型に入っておらず、点の理由にもならない。画面の理由は「弱点を受けられる」が中心。**集計がある本番では型が変わる**ので、そこは別に確かめる必要がある。
- **[確認] シングルとダブルで同じ順位。** 集計なしの状態で、同じ5匹から `prRank` の上位5匹がシングルとダブルで同じだった。`prScore` は形式を見ていない（形式で変わるのは、集計の「一緒に使われる」と上位構築、`prHit` の鍵だけ）。ダブルで大事な補助（ねこだまし・おいかぜ・このゆびとまれ・範囲技・味方への影響）は点に入らない。

## D. これからの評価の仕組み（提案。まだ作らない）

**数字の重みはここでは決めない。** まず「何を比べるか」を決め、重みが要るなら C の証拠で決める。

### 層1：ルールとデータの確認
- 現行レギュレーションで使えるか（ポケモン・持ち物・メガストーン・技・特性）を1か所で判定する関数。使えない候補・型は出さない。
- メガシンカは「パーティでだれがするか」を1つに決め、計算は「その匹だけメガの姿」。複数メガを持つパーティは「メガの選び方ごと」に分けて評価。
- 入力：公式の一覧（C の1・2）。証拠：公式で確認。分からない所は「未確認」として画面に出す。

### 層2：1匹ずつの対戦の強さ
- 1対1の判定を `dgMatch` の1つにそろえる（`estHit`・`duel`・`monCounters` は置きかえ）。
- 段階は「タイプで受けられる」「1回は耐える」「交代で出て勝てる（`swIn`）」「先に出て勝てる」「全体で有利」を**別の項目**として持つ（混ぜて1つの点にしない）。
- 素早さは「基準の相手より速いか」を、相手の実際の型（性格・能力ポイント・スカーフ）で。

### 層3：パーティの形
- 役わり：実際の型（登録した育成、なければ集計の型）の技・特性から決める。「覚えられる」は候補の可能性として別に持つ。
- 天気・トリックルーム・おいかぜ：起こす匹と使う匹が**型の上で**そろっているか。
- 役の重なり：同じ相手に有利な匹が多いことと、失われる役（勝ち筋・後出し・速さ）を両方見る。

### 層4：選出
- シングル（3匹）とダブル（4匹・先発2）を別の評価にする。ダブルの補助・範囲技は、計算できないうちは「未評価」として出す。
- パーティの評価は「良い選出がいくつ作れるか、どの相手に対して」で見る（6匹の合計で見ない）。

### 層5：入れかえの比較
- 入れかえを出す所を1つにまとめる（今の①〜⑤）。
- 変更前と変更後を**同じ相手・同じ型・同じデータ版**で計算し、層2〜4の項目ごとに「良くなる・悪くなる・変わらない」を相手の名前つきで出す。
- 候補には、入れる型（集計の型・型の例）とメガシンカの扱いを必ず決めてから計算する。決められないときは出さないか「型を決めてください」。

### 層6：説明と確かさ
- 出すもの：何が良くなるか・何が悪くなるか・どの問題を直すか・新しく増える弱点・前提（集計の有無と日付、相手の型、メガ、形式）・確かさ（使ったデータの出典の分類）。
- 合計点が高いだけでは出さない。良くなる所と悪くなる所が両方あるときは「交換」として並べ、選ぶのは利用者。
- 証拠が足りないときは「判断できません（理由）」と出す。

| 決まったパーティ | シングル・ダブルそれぞれ、よく使われる構築の型（天気・トリックルーム・対面・サイクル・積み）を各数個 | 同じ入力で毎回同じ結果（データ版を固定） |
| 大会の上位パーティ | C の大会データから、レギュレーション・形式ごと | 1匹を「外して」入れかえ案を出すと、元の匹か同じ役の匹が上位に出る（再現率を測る。何%で合格かは件数を見て決める） |
| 問題のある形 | 弱点が3匹以上重なる・メガ3匹・遅いのにトリックルームなし・全員物理 等 | 問題を指摘し、直す案がその問題を減らし、新しい問題を増やさない |
| 相手のパーティ | 上位の構築を相手として固定 | 入れかえ前後で、相手ごとの結果が説明と一致 |
| メガシンカ・姿 | メガ2匹のパーティ、メガストーンを持つ匹を外す案、ギルガルド・イルカマン・ミミッキュ | 同時に2匹メガで数えない・メガの数の変化を知らせる |
| 後出し | 交代で受ける1発目を耐える／耐えないの境目 | `swIn` の境目が計算どおり |
| ダメージ | 既存の calc-ref・calc-cases・disguise | 今と同じく全部合格 |
| 説明 | 画面の文と、計算の中身を突き合わせる自動テスト | 出した理由が、実際に点や判定を変えた項目と一致 |

リリースの条件：上のすべてに合格、データ版（集計の日付・レギュレーション）を画面に出す、未確認の前提を画面に出す。

## F. これからの順番

1. **すぐ直すべき誤り**
   - メガシンカの同時計算（B-1-1）。証拠：公式の「1試合1匹」の確認（複数の資料は一致）。
   - 入れかえでメガの数が変わることを知らせる（B-1-2）。
   - 見出し「理由の多い順」と並びの不一致、△に wall が入る扱い（B-1-3・4）。説明を合わせるか、段階の定義を決め直す（依頼主の判断）。
2. **ゲームのデータ**
   - 現行レギュレーションで使えるポケモン・持ち物・メガストーンの一覧（C の1）。候補の絞り込みに必要。
   - メガシンカの素早さの時期、タイプ相性のゲーム内での確認。
3. **評価の考え方**
   - 1対1を `dgMatch` にそろえる。候補を「実際の型」「メガの扱い」を決めてから評価する。
   - タイプの受け合いの点を、実際のダメージの結果（層2）で置きかえる。
4. **候補の集め方**
   - 入れかえを出す所を1つにまとめる。シングル・ダブルを分ける。勝ち筋の匹を守る仕組み（軸を付けなくても）。
5. **説明と画面**
   - 良くなる・悪くなるを相手の名前つきで、前提とデータ版を出す。点数は出さない（今と同じ方針）。
6. **対戦データの取りこみ（長期）**
   - 標本数・期間・勝率のある集計（C の3・4）を比べて選ぶ。大会の上位パーティを検証用のデータにする。

各項目は、実装の前に C の証拠を集めてから進める。

## G. この点検の限り

- 外への通信を止めた状態（集計なし）で動かした。本番（集計あり）の結果は確かめていない。とくにエルフーンの例は、集計がある本番では型が変わる。
- 読んだのは上の表のファイルの関係する部分。`13-party.js`・`60-diag.js`・`40-guide-builds.js`・`39-guide-mons.js` は大きいので、評価にかかわる関数を中心に読み、画面の部分はすべては読んでいない。
- 外の出典は検索結果の要約が中心で、ページを開いて確かめたのは Showdown のソース（ばけのかわ）だけ。公式のレギュレーションのページは見つけられなかった。
- 失敗の例は2つのパーティで確かめただけで、件数は少ない。
- ゲームでの確認はしていない（ゲーム機がない環境のため）。
