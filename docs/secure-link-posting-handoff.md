## Feature contract
1. Authenticated timeline notes and replies only; anonymous boards/lobby, DM/group DM, profile, other user fields remain under existing policy. DM/other contexts may be a separate later review; do not enable by accident. Preserve 140 Unicode code point text limit, image limits, 15s/100 per day note rate and report threshold. Proposed MVP: at most ONE user HTTPS URL per note/reply; provide dedicated optional URL field (max 2048 UTF-8 bytes) so long guide URLs do not consume the 140-character text budget. Support pasting a single full HTTPS URL into composer/reply and moving it to the URL field explicitly/visibly, preserving surrounding prose; API handles inline link consistently (extract exactly one or reject with actionable message; no silently dropped text, no duplicated URL). Reject invalid or multiple candidates; document canonical storage and validation order. Require nonempty text OR existing valid media OR accepted URL. Check bounds before normalization, no silent truncation; reject unexpected types. Retain old clients' behavior when disabled. Use separate user-link metadata from bot notes.link, with state, verdict timestamp and expiry; include only authorized visible note metadata in feeds/replies/reposts/search/profile/bookmarks/admin as needed. Never leak hidden/private notes. No arbitrary HTML/Markdown links or previews. Future party-code/game-scoped links may use separate validated typed metadata; do not implement party import or other games now.
2. Server is authoritative; client mirrors only for UX. Parse using WHATWG URL after strict bounded tokenization; HTTPS only, explicit scheme, no credentials, non-default ports, IP literals/local/single-label/internal destinations, controls, bidi/zero-width ambiguity, backslashes, deceptive userinfo or malformed encoding. Treat Unicode/IDN conservatively (reject or show canonical ASCII/punycode); disallow known shorteners and open-redirect patterns as feasible, not as security guarantee. Do not turn bare/obfuscated domains or other schemes into links. Preserve NG words and external-contact restrictions where applicable; do not allow forbidden terms or personal contact to bypass filtering via URL or masking. Prefer safe rendering with DOM textContent/createElement, or audited context-aware escaping of text/attributes plus strict validation; revalidate on render/click and handle legacy/untrusted API rows as inert. URLs never become hashtags. Actual canonical host and full destination visible in confirmation dialog; deliberate click only, keyboard-accessible, no opener/referrer (rel="noopener noreferrer nofollow ugc", target="_blank"), no untrusted innerHTML, no javascript/data/blob/file/mailto/tel, no auto-navigation/router injection. Preserve existing trusted bot internal routing without generalizing it to user URL. No remote thumbnails, iframes, embeds, prefetch, redirect-following, proxy, DNS probing or fetch of posted destinations from Worker or browser prior to explicit consent.
3. Threat checks: use server-side Google Cloud Web Risk Lookup (or equivalent approved commercial provider) through isolated adapter, only fixed provider endpoint, server secret never bundled/logged. Send canonical destination only; warn against private/auth-token URLs and reject obvious sensitive URL parameters; document third-party data transfer and obtain owner policy approval. No automatic external threat submissions. Validate provider response, cap response bytes, timeout, concurrency, requests per UID/global, cache bounded results using provider expiry and shorter local maximum; fail closed (reject new URL or leave inert pending on outage, quota, malformed response, missing key, stale verdict). Non-link posts must remain usable even if checker unavailable. Check all required threat types; never claim clean means guaranteed safe. No direct target fetch. On click, require fresh verdict via bounded first-party API, revalidate current authorization/visibility/state, then user-confirmed external navigation (avoid open redirect endpoint). A link changed/flagged after posting must become inert; implement bounded recheck/report/admin takedown, not a global unbounded crawl. No auto-ban on URL scanner flag, timeout, syntax rejection or reports alone; log limited sanitized evidence and quarantine confirmed unsafe links/post. Abuse/spam quotas must also cover rejected requests and parallel submissions; no unbounded body read, regex backtracking, database writes or external requests. Use atomic enforcement or demonstrate races cannot bypass limits.
4. Moderation: preserve current manual users.banned; add durable, reasoned sanctions by immutable UID, permanent or time-limited (proposed 90 days default for confirmed related violating accounts, configurable 3–6 calendar months; owner approval before release), evidence ID, source, actor, timestamps, status, expiry, appeal/reversal and audit events. Manual review required for intentional malicious link/system attack; confirmed perpetrator gets permanent UID + verified-email denylist, confirmed linked account gets temporary restriction. Suspicion, shared IP/device/network alone, ordinary user errors, reports or provider hits are insufficient; no invasive fingerprinting, automatic collective punishment, or exposing linkage to others. Use only lawful, approved evidence; no unsupported identity inference. Temporary expiry must apply consistently to reads/writes and visibility without accidentally unbanning permanent/manual bans. Reuse existing admin authorization, require reason and explicit confirmation; sanitize admin views; reports remain moderation input, not proof. No client-controlled ban flags or identity.
5. Verified email registry: use verified Firebase token claims (never request body); store keyed HMAC-SHA-256 of carefully defined normalized verified email only, separate secret with rotation/version plan, no raw email in moderation logs or public responses. Avoid provider-wide plus/dot alias folding or false associations; define normalization and test it. Associate verified email with UID at verified sign-in/authorized calls before allowing link creation; handle changes, absent/unverified email, stale claims and deletion safely. Permanent email tombstone survives account deletion according to approved retention/legal policy; enforce even for new UID without profile and preexisting sessions, across all authenticated privileged actions, not just /api/me or UI. Do not block ordinary anonymous reading. For existing offenders lacking verified email evidence, flag as unresolved, no invented association. If Firebase Auth account disable/revoke is desired, document necessary Admin permissions and test with mocks; do not assume current Workers token verifier revokes tokens or prevents Firebase-side account creation. Service-side re-registration/usage denial is mandatory; actual Firebase registration prevention requires separate verified auth infrastructure. Distinguish these in release report. No production keys/data; no raw email backfill from guessed data. Ensure approved retention/deletion/appeal and access control, secure migration (idempotent, additive, indexed, backwards-compatible, no destructive changes). Preserve existing legitimate ban/unban semantics; prevent old unban route bypassing active sanctions. Fail closed for sensitive actions if sanction store unavailable.
6. Update Japanese/English rules, privacy notice, composer guidance and admin reason strings; distinguish timeline URL allowance from DM/anonymous prohibition. State threat-check limitations and intentional-attack sanctions. Do not change actual legal policy without owner approval. Include feature flag/kill switch, rollback runbook (disable publishing/clicking without deleting posts or sanctions; preserve existing moderation; safe client/Worker mixed versions).
