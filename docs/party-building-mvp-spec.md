# 入れかえ案 MVP 第1段階：ルールとデータの仕様（2026/11/13）

目的：6匹のパーティの大きな弱点を見つけ、**現実的な**入れかえ候補（使える型・メガシンカの決まりを守る）を出す MVP のための、ルールとデータの土台だけを決める。
この文書は仕様だけ。プログラム・計算・画面は変えていない。前の点検は `docs/party-building-audit.md`。

表記：**[確認]**＝この調査で一次資料を読んで確かめた／**[推定]**＝根拠はあるが確定していない／**[未確認]**＝資料がない。
取得日はすべて 2026/11/13（UTC）。

## 0. 確定した決定（2026/11/13 依頼主。第2段階はこれに従う）

- **A 使えるか**：中の鍵は公式の「図鑑番号-姿の番号」。名前では決めない。M-C で使えると確認できた姿だけを、ふつうのおすすめに出す。対応が [推定] の姿は「未確認」として、ふつうの順位から外す。図鑑にある・使用率にある、では決めない。公式ページの「新しくメガシンカできる6つ」を、使えるメガストーンの全部とみなさない。確認できていないメガストーン・持ち物は「未確認」のまま表示する。
- **B 型のデータ**：MVP の型は **PokéKit を第一の出典**にする（出典・形式・月・対戦数が書いてあるため）。PokéKit は Smogon / Pokémon Showdown の集計で、ゲーム内の公式の集計ではないと明記する。シングルとダブル、出典・形式・月を混ぜない。別のデータの項目をつなげて型を作らない。自動で作った型（`chooseSet` 等）を候補にしない。確かめた型がない匹は「データ不足」として、ふつうの順位から外す。上位150匹の限りを守る。**PokéKit の `evs` はチャンピオンズの能力ポイントとして使わない**（形は合うが未確認）。
- **C 評価の範囲**：6匹全体を評価する。3匹・4匹の選出の組み合わせは数え上げない（選出アシストの役目）。シングルとダブルは別のデータ・別の評価。ダブルの ねこだまし・おいかぜ・範囲技・味方との関わり等は**評価していない**と明記する。
- **D メガシンカ**：1対戦1回。メガシンカできる匹は何匹でもよい。メガシンカする匹ごとに別の場合として計算し、2匹を同時にメガの姿で数えない。メガシンカできる匹の数を決めつけない。入れかえで最後のメガシンカできる匹がいなくなるなら警告、増えるならメガの場合が変わると出す。未確認のメガストーンを使えるとみなさない。
- **E 持ち物**：参加させる匹のうち2匹以上が同じ持ち物は不可。**6匹全体**で守る。候補の型の持ち物が残りの5匹と重なるなら、その型では出さない。同じデータに無い持ち物にこっそり替えない（同じ出典・同じ形式・同じ月のその匹の持ち物の一覧にあるものだけ）。替えられなければ「使えない／データ不足」。
- **F 説明**：確認した事実・出典のデータ・推定・不明を分けて書く。使われていることを強さの証拠にしない。1対1で勝つことを「安全に後出しできる」と言わない。「1対1で有利」「交代で受けられる（後出し）」「6匹全体が良くなる」を分けて書く。

## 2. 現実的な型（技・特性・持ち物・能力ポイント）の出典

**出典ごとに分けて持つ。割合・対戦数・勝率を混ぜない。**

### 2-1. PokéKit 使用率オープンデータ [確認]
説明：https://poke.itlibra.com/en/opendata　ファイル：`https://poke.itlibra.com/opendata/usage-{format}.{csv|json}`

| 項目 | 内容 |
|---|---|
| もとのデータ | Smogon が公開する **Pokémon Showdown のランク対戦の月ごとの集計**（chaos 形式）。公式のゲーム内のデータではない |
| チャンピオンズ | `championssingles`＝「Champions BSS reg.MC」シングル・**2026-10・87,848戦**／`champions`＝「Champions VGC reg.MC」ダブル・**2026-10・1,649,648戦**。どちらもレート1760以上（cutoff） |
| 範囲の限り | 各形式の**上位150匹だけ**。M-C の262匹のうち少なくとも112匹は入らない（そういう匹は「型の資料が足りない」扱い） |
| 1匹ごとの中身（JSON） | rank・id（Showdown の名前）・num（図鑑番号）・types・baseStats・usage（形式全体での割合）・abilities（最大4）・items（最大6）・moves（最大10）・tera・spreads（最大4：nature と evs）・teammates（最大8） |
| 割合の意味 | usage は形式全体に対する割合。技・持ち物・特性・テラ・振り方・仲間は「その匹を使った人の中で」の割合（分母が違う） |
| メガの扱い | メガの姿は**別の行**（例 `charizardmegay`・`garchompmegaz`）。元の姿の行とは別に数えられている |
| 更新 | 毎月15日ごろ、前の月のぶん。**最新の1か月だけ**配布（過去は Smogon から） |
| 利用条件 | 無料・再配布可・商用可。「Smogon / Pokémon Showdown」と「PokéKit」の両方を表記。サーバーに負荷をかけない（利用者が多いアプリは自分のサーバーに1回取ってから配る） |

チャンピオンズに使えるか（このファイルを調べた結果）：
- **tera**：2形式とも全部空。**使わない**（チャンピオンズにテラスタルはない）。
- **持ち物**：`nothing`（持ち物なし）と `leek`（＝ながねぎ。サイトでは stick）以外は、サイトの `CH_ITEMS`＋メガストーンに入っていた。
- **spreads の evs**：600件すべて「合計66以下・1つ32以下」。チャンピオンズの能力ポイント（合計66・1つ32まで）と同じ形に見える。Showdown のチャンピオンズ用データがポイントをそのまま書いていると [推定]。**変換はせず、この形のまま、確かめるまでは「要確認」とする**（前の世代の努力値として読み替えない）。
- **技・特性**：Showdown の名前。サイトの覚える技・持てる特性と照らし合わせてから使う（合わないものは捨てる）。
- 公式のゲーム内の集計ではないので、「Showdown の対戦での使われ方」と表示する。

### 2-2. いまサイトが使っている championsbattledata.com
- ブラウザから直接、ポケモンごとの CSV を読む（`15-battle.js` の `liveInit`・`liveMon`）。持ち物・技・特性・性格・能力ポイント・仲間。
- **集め方・対戦数・期間がデータに書かれていない**（サイトの `SRC.ladder` も「集計の方法は公開されていません」）。ファイル一覧は Doubles のフォルダ名から作っている（シングルにだけある匹は読めない [推定]）。
- PokéKit とは別の出典として扱い、数を混ぜない。

### 2-3. 型の決め方（MVP）
1. 候補1匹の型は、**PokéKit の、同じ形式の、同じ月**のその匹の行だけで組む（持ち物・技・特性・性格を別々の出典から取らない）。
   PokéKit は項目ごとの割合だけで、組み合わせの割合は無い。各項目で割合のいちばん高いもの（使えるもの）を選び、そのことを画面に書く。
2. 組んだ型は、M-C で使えるか（1章）・覚える技・持てる特性・持ち物の一覧（`CH_ITEMS`・その匹のメガストーン）・パーティの持ち物の重なり で確かめる。
3. 型が組めない・確かめられない候補は「データ不足」として、**自分で型を作らない**（今のサイトの自動の型 `chooseSet` は MVP の候補には使わない）。
4. 能力ポイント：PokéKit の `evs` は使わない（未確認）。計算はすべての候補・相手で同じ**仮定の振り方**（攻撃側の能力32・素早さ32・HP2、性格は PokéKit の割合のいちばん高い性格）で行い、「能力ポイントは仮定」と画面に出す。
5. 型には出典名・形式・月・対戦数・取得日を付けて、画面に出す。
6. いまのパーティの匹：登録した育成があればそれ。無ければ同じ形式の PokéKit の型、それも無ければ今の自動の型（「推定」と表示。候補ではないため可）。

## 3. シングルとダブル（MVP に関係する所だけ）

- データは形式ごとに完全に分ける：PokéKit は `championssingles` と `champions`、championsbattledata は `Singles` と `Doubles` のフォルダ。片方が無いとき、もう片方で代えない。
- 6匹の評価は、利用者が選んだ形式（サイトの `FMT`）のデータ・相手の候補だけで行う。
- 公式ページに、シングル/ダブルで連れていく数・選ぶ数の記載はない [未確認]。サイトは シングル＝6匹から3匹・ダブル＝6匹から4匹（先発2）としている。
- **選出の組み合わせ（3匹・4匹のどれを出すか）は入れかえ案では計算しない。** 今の選出アシスト・選出の比較（`dgSelect`）が受け持つ。
- ダブルの補助（ねこだまし・おいかぜ・範囲技など）は MVP では評価しないと明記する。

## 4. メガシンカと持ち物の決まり

| 決まり | MVP の扱い |
|---|---|
| 1回の対戦でメガシンカは1度だけ [確認] | パーティにメガストーンを持つ匹が何匹いてもよい。ただし**計算は「だれか1匹だけがメガシンカした場合」ごとに分ける**。2匹以上を同時にメガの姿で数えない（今の診断 `dgTeam0` はこれを守っていない＝点検報告 B-1-1） |
| メガシンカできる匹の数 | **決めつけない**。0匹・1匹・2匹以上のどれでもよい（どれかに寄せない） |
| メガの案の比べ方 | メガシンカできる匹が2匹以上なら、「Aがメガ」「Bがメガ」それぞれの結果を並べて出す（どちらが良いかは相手しだいなので、1つの点にまとめない） |
| 入れかえでメガが無くなる | 外す匹がメガストーンを持ち、入れかえでメガシンカできる匹が0になるなら、その案に「メガシンカできる匹がいなくなる」と必ず出す（止めはしない） |
| 入れかえでメガが増える | 候補がメガストーンを持つ型なら、メガの案が1つ増えたと出す |
| 同じ持ち物は2匹まで不可 [確認] | 公式の文は「参加させるポケモンのうち2匹以上に同じ持ち物は持たせられない」。**パーティ全体で同じ持ち物を禁止**する（選出だけでなく）。候補の型の持ち物が残りの5匹と同じなら、その出典の次の持ち物にし、それも無ければ「型の資料が足りない」 |
| メガストーンも持ち物 | 同じメガストーンを2匹は持てない（上と同じ決まり） |
| M-C で使えるメガストーンの一覧 | [未確認]。公式ページは新しく足された6つだけ。全部の一覧を手に入れるまで、メガの候補には「要確認」を付ける |

## 5. データの届け方（軽く・安全に）

いまの形：サイトは Cloudflare Pages の静的なファイル。サーバー（Workers）は無料枠（1日10万回）を気にしている。集計は利用者のブラウザが championsbattledata を直接読んでいる。GitHub Actions は main への push と毎朝5:07（日本時間）に組み立てて公開している（`deploy.yml`）。

第2段階で採った形（2026/11/13）：取得した PokéKit の2つの JSON と公式の一覧を、手で動かす変換の道具（`tools/gen-mvp-data.cjs`）で確かめて小さくし、**版（月・取得日）の付いたデータのファイル**（`src/js/75-mvp-data.js`）としてリポジトリに置く。サイトの組み立てで1本の JS に入り、Pages から配られる。利用者のブラウザは PokéKit を読まない。通信を待たないので、同じ入力なら同じ結果になり、読み込み途中の結果も出ない。自動で定期的に読む仕組みは作らない（月1回の更新は、依頼主の確認のあとに道具を動かす）。

当初のおすすめ（自動化するときの形）：
1. **月1回、GitHub Actions** で PokéKit の2つの JSON と、公式の「参加できるポケモン」のページを読む。
2. 形を確かめる（1章・2章の確認、件数・月・形式・tera が空・能力ポイントの範囲）。**だめなら前の版を残して失敗にする**（中途半端な版を出さない）。
3. 通った分を、**版の付いた静的な JSON**（例 `dist/assets/data/mc-legal-2026-11-13.json`・`pokekit-champions-2026-10.json`）にして、今のサイトの公開と一緒に Pages から配る。中に出典・月・対戦数・取得日・確認の結果を入れる。
4. 変わったときは、更新の案として依頼主が確認してから反映する（2026/11/09 の方針「週1回の更新の案→依頼主が確認」に合わせる）。

しないこと：利用者のブラウザから PokéKit を直接読む（PokéKit の利用条件・CSP の追加・失敗のときの扱いが増える）、Workers で毎回読みに行く・独自の保存の仕組みを作る。
月1回の読み込みは Actions の範囲で足り、Workers の回数は増えない。毎朝の組み立てで毎回読みに行く必要はない（PokéKit は月1回しか変わらない）。

## 7. MVP の範囲

**やる**：
- M-C で使える匹だけを候補にする（1章のデータ）。
- 候補の型は1つの出典・同じ形式・同じ月から。組めなければ「確認不足」と出す。
- メガシンカは1匹ずつの場合で計算・メガが無くなる/増えることを出す。
- 同じ持ち物を2匹に持たせない。
- 6匹の大きな弱点（点検報告の「×」「後出しできない」等、今の `dgMatch` の結果）を直す候補を、変更前→変更後で出す。

**やらない**：
- 選出の組み合わせの計算（選出アシストに任せる）。
- 6匹全部を最適にする計算。
- ダブルの補助・範囲技の評価。
- 自動で型を作ること（出典の無い型は出さない）。
- 勝率・大会の結果の取り込み、出典どうしの数の合算。
- 新しいサーバーの仕組み・データの保存の仕組み（第2段階で静的な JSON から始める）。
