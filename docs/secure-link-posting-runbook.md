# Secure link posting — configuration, rollback and policy drafts

Status: implemented on `feature/secure-link-posting`, **all flags OFF by default, not released**. Do not enable in production until every gate in `docs/secure-link-posting-report.md` §7 is closed.

## 1. Server flags and secrets (Cloudflare Worker settings — names only)

| Name | Kind | Default | Effect |
|---|---|---|---|
| `LINKS_POST` | variable | unset (OFF) | `1` = authenticated timeline notes/replies may carry one HTTPS link. Also requires `SANCTIONS_ON=1`, a valid email keyring with a current version, and `WEBRISK_API_KEY`; otherwise link posts are refused (503) and plain posts are unaffected. |
| `LINKS_CLICK` | variable | unset (OFF) | `1` = links can be opened through the two-step `open` → `go` flow. OFF = feeds return `state:"off"` (host only) and both endpoints return 403 `inert`. |
| `SANCTIONS_ON` | variable | unset (OFF) | `1` = admins can create case records and sanctions; verified-email hashes start being recorded. **Active sanctions are enforced regardless of this flag.** |
| `WEBRISK_API_KEY` | secret | unset | Google Cloud Web Risk key, sent only in the `x-goog-api-key` header to the fixed endpoint `https://webrisk.googleapis.com/v1/uris:search`. Never returned or logged. |
| `EMAIL_HMAC_KEYRING` | secret | unset | JSON `{"<version>":"<key ≥32 chars>", …}` (≤32 versions, version = `[A-Za-z0-9_-]{1,16}`). **All versions still referenced must stay in the ring, and a version's key material must never change** (checked against `key_sentinels`). |
| `EMAIL_HMAC_KEY_CURRENT` | variable | — | Version used for new hashes. Must exist in the ring, or the ring is treated as invalid. |
| `EMAIL_HMAC_KEY` / `_VER`, `EMAIL_HMAC_KEY_PREV` / `_PREV_VER` | secret / variable | unset / `v1` / `v0` | Legacy single-key form; merged into the ring (`EMAIL_HMAC_KEY` is current unless `EMAIL_HMAC_KEY_CURRENT` says otherwise). |
| `LINKS_WEBRISK_DAY` | variable | `3000` | Global daily cap on provider calls (UTC day). |
| `LINKS_WEBRISK_MONTH` | variable | `90000` | Global monthly cap (UTC calendar month). Day and month are reserved together in one conditional upsert on the day row of `link_budget_d` (month = sum of that month's days), only after a lease is held; admitted calls count even if they fail; cache hits never count. |
| `LINKS_WEBRISK_CONC` | variable | `4` | Global concurrent provider calls (1–16), enforced by D1 lease rows shared by every isolate. |
| `LINKS_WEBRISK_MS` | variable | `3000` | Provider timeout (500–5000 ms). A lease expires at timeout + 2 s, so a crashed isolate's lease is recovered automatically. |
| `LINKS_CLEAN_TTL_MIN` | variable | `30` | Local lifetime of a "no match" verdict (5–60 min) — a site policy, not a provider guarantee. Unsafe verdicts are kept exactly until the provider's `expireTime` (no cap, and a forced fresh lookup never shortens them); a missing/invalid `expireTime` is treated as malformed (fail closed, not cached); a past `expireTime` denies the current operation without caching. |
| `FB_ADAPTER_TOKEN` | secret | unset | ≥32 chars. Lets `tools/firebase-adapter` use `/api/fb/claim`, `/api/fb/intent`, `/api/fb/ack`. Separate from `ADMIN_TOKEN`. Unset ⇒ endpoints return 404. |
| `ADMIN_REVIEWER` | variable | unset | Name of the single owner who reviews cases. Set ⇒ every case, sanction and email release records `reviewer = owner:<name>` assigned by the server (any submitted name is ignored). Unset ⇒ the submitted name is stored as `self:<name>` (self-asserted under the shared `ADMIN_TOKEN`, not an authenticated identity). **Multi-staff operation needs per-staff authentication/authorization and an immutable audit trail before enabling — not implemented.** |
| `FB_HOOK_TOKEN` | secret | unset | ≥32 chars. Lets the blocking functions call `/api/fb/check` (answer is `{deny}` only). Unset ⇒ 404. |

No new binding is required; all new tables live in the existing D1 (`DB`).

## 2. Enabling (only after the release gates)
1. Create the keyring as a secret (`EMAIL_HMAC_KEYRING`, random keys ≥32 chars) and set `EMAIL_HMAC_KEY_CURRENT`. Set `WEBRISK_API_KEY`.
2. `SANCTIONS_ON=1` first and check the admin tab「リンク・利用停止の記録」: the key-status banner must be absent (`health.ok`).
3. `LINKS_CLICK=1`, then `LINKS_POST=1`. `GET /api/links/config` must return `{"post":true,"click":true}`.
4. Apply the approved rules/privacy text (§5) in the same release.

## 3. Behaviour that operators must know
* **Opening a link (two steps).** Feeds return only `{host, state}` (`ok` | `off` | `blocked`), never the full URL. `POST /api/links/:id/open` re-checks visibility, state and a fresh verdict (re-reading them after any asynchronous re-check) and returns the URL for the confirmation dialog plus a one-use intent valid 60 s and bound to the viewer and the link's revision. `POST /api/links/:id/go` consumes the intent atomically and re-checks visibility, state, revision, verdict expiry and the flag before returning the URL. The browser opens a blank tab inside the click, clears `opener`, and navigates it through a `no-referrer` meta refresh only after `go` succeeds; on any refusal the tab is closed. If the browser blocks the tab, **no `<a href>` is ever rendered**: a 「もう一度開く」 button appears for 30 s; pressing it opens a blank tab inside that click and repeats `open` (new intent) → `go`, so a link quarantined in between is refused. If tabs are still blocked, the user is asked to copy the address already shown in the dialog.
* **Limits that cannot be removed:** a URL already shown in a dialog (or copied) cannot be revoked from the user's memory; there is an unavoidable race between the final `go` answer and the external navigation; a destination can change after it was checked. "No match" is never presented as "safe".
* **State changes are revision-guarded.** Every state change on `note_links` increments `rev`. Re-checks (click, report) and admin restore/recheck write only if `rev` is unchanged since they read it; admin quarantine always wins and increments `rev`, invalidating outstanding intents.
* **Replies and private accounts.** Every reply (with or without a link) checks, inside the same INSERT, that the parent is still visible to the author (not hidden, author not banned, private author only for the owner or an approved follower; pending requests do not count). Like, repost and bookmark use the same visibility rule (404 = not found, no notification). Previously plain replies, likes, reposts and bookmarks to a private post could be made by anyone who knew its id (and notified the owner).
* **Provider budget and shared verdicts.** Shared cache (key = policy version + canonical URL without fragment) → lease (global, D1) → day+month budget → fetch → release. Every publish, `open` and `go` consults the shared verdict, so an unsafe answer for the same destination found through another post makes this post inert before its own TTL; `go` reads the consumed intent, the post's visibility, the link row and the shared verdict in one D1 batch (one transaction) at response time. An unexpired unsafe answer always overrides a clean or shorter-lived unsafe row regardless of response order (an older request's unsafe answer that arrives after a newer clean one still wins); a clean answer overwrites only an older clean row. Real bounds: clean rows are cached only while there are fewer than 5000 active unsafe rows and total rows are trimmed to 5000; unsafe rows are cached up to 20000 and never evicted while valid — beyond that a new unsafe answer is not cached, but the post is refused/marked unsafe and other posts with that destination are re-checked each time (fails towards blocking). Day and month are independent buckets (`link_budget_d`: one row per UTC day, month = sum of its days), reserved in one conditional upsert at the actual admission time (after the lease, just before the call): an out-of-order or delayed request is counted in its own day/month and never resets or moves another bucket (reviewer's reproduction: Nov 30 at 2999/89999 → Dec 1, delayed Nov 30, Dec 1 ⇒ Dec = 2, Nov 30 = 3000). Rows whose cache key was made under an older policy version are re-keyed when opened. A cache read/write failure fails closed for links only.
* **Unsafe-cache saturation (fail closed, round 5).** Admission into `link_verdicts` is one statement that counts active unsafe rows and inserts/upserts only below the cap (unsafe ≤ 20000, clean only while unsafe < 5000); converting a clean row to unsafe counts as a new unsafe row; extending an existing active unsafe row is always allowed. Whenever an unsafe answer arrives, every existing `ok` note with the same cache key is marked `unsafe` (and `rev` bumped, invalidating outstanding intents) whether or not the verdict could be cached — positive threat knowledge is never silently dropped. If an unsafe answer could not be cached, the durable flag `link_state.wr_saturated` is set: while set, link publish, `open`, `go` (including already-issued intents) and admin restore/recheck all fail closed (503 `saturated` / 409) and the provider is not called (a cached unsafe hit is still answered). The flag is persisted in D1 (survives restarts) and records `until` = the latest `expireTime` of any unsafe answer it could not cache (raised with `MAX`, never lowered). Round 6: the flag is also checked **inside the final write** of every gated operation — the note INSERT (`noteIns`), the intent INSERT on `open` (which also re-checks state, `rev`, `pol`, clean expiry and the shared unsafe verdict), the intent-consuming UPDATE on `go` (same batch also reads the flag, so a flag raised between the pre-check and the commit returns 503 and leaves the intent unused), and admin restore/recheck clean writes — so a flag raised between the pre-check and the commit still blocks. Recovery is one conditional `DELETE` that removes the flag only when `until` has passed **and** active unsafe rows are below 90 % of the cap; a concurrently re-raised flag (later `until`) is therefore never deleted, and no uncached unsafe answer is forgotten before its own expiry. Irreducible: after `go` has answered, the browser's navigation cannot be revoked (the answer is the last server decision). Shown in the admin tab (`link_saturated`). Plain posts are unaffected.
* **Policy binding (round 5).** `LK_POLICY` (threat-type list + version) is part of the cache key `vh` and stored on each link (`note_links.pol`) and each intent (`link_intents.pol`). On `open`, a link with an older `vh` or `pol` is re-keyed with `expires_at=0` and `rev+1` (old intents die; a fresh check under the current policy is required — the old clean TTL is not carried over); a cached unsafe under the old key is applied first, and an existing `unsafe` state is never cleared by a policy change. `go` refuses (410 `expired`) unless both the intent and the link carry the current policy. Admin restore/recheck stamp the current policy. The old single-row budget table `link_budget` (pre round 4) is migrated once into `link_budget_d` in the same init batch (day row + a `YYYY-MM-00` filler row for the rest of the month total, then the old row is zeroed) so an upgraded system never silently resets its quota.
* **Request bounds.** JSON bodies are read as a stream and cancelled at 256 KB (with or without `Content-Length`); only JSON objects are accepted. Malformed bodies count per client (salted IP hash): 30 per 10 min per client, 5000 per 10 min globally, then 429. Link intents (field present or `http(s)://` in text) take the per-UID slot (10 s / 12 per h / 40 per day) before any other check, including malformed ones. Every note insert enforces 15 s / 100 per day inside the INSERT itself, so concurrent plain and link posts cannot exceed it.
* **Case records (evidence).** `POST /api/admin/cases` requires: target, kind `attack`|`linked`, summary ≥20 chars, 1–10 references to this site's own records that belong to the target (note, link, link_event, report — never IP/device), `attest:true` (the reviewer personally checked the evidence), `reviewer` (the reviewer's name, 2–40 chars — the shared admin token cannot identify individuals, so the name is recorded together with the token/IP pseudonym; per-staff credentials are a release recommendation) and `evidence_kinds` containing `direct` (the target's own wrongdoing). The case stores `signals` computed from the references (`staff_quarantine`, `scanner_unsafe`, `report`) so automated verdicts are kept separate from staff decisions; evidence is stored as references to this site's records, not copies. A **linked** case additionally requires `linkage` in `evidence_kinds`, `linkage_basis` ∈ `self_admitted` / `evasion_after_sanction` / `coordinated_reviewed`, a `direct_summary` ≥20 chars of what the target personally did, a `linkage_summary` ≥20 chars of independent linkage evidence, an active confirmed-attack parent root, a target link with the same destination as a link in the parent's case, **and** a target link that **staff quarantined** (a scanner `unsafe` verdict alone is not evidence of intent). `shared_url`, `ip`, `device`, `report` and `scanner` are explicitly rejected as linkage bases: a shared destination (e.g. someone reposting a guide), IP, device, reports or a scanner verdict alone never makes a linked case (no guilt by association). Evidence kinds and basis are stored on the case (`ek`, `lbasis`, `dsum`).
* **Sanctions.** `POST /api/admin/sanctions` needs the open case, rationale ≥20 chars and `confirm:"SANCTION"`. **Permanent** (`perpetrator`) additionally needs `basis` = `deliberate_attack` or `proven_evasion`; an unsafe verdict alone is never a basis. Every sanction row stores `basis` (`deliberate_attack`/`proven_evasion`/`linked`/`temporary`) and `reviewer` in dedicated columns (timestamps `created_at`/`updated_at`; audit events in `sanction_events`). The UID row, email tombstones, audit events, `banned=2`, the Firebase sync touch and the case status are written in one D1 batch under one immutable `root_key`. Reversal reverses every row with that `root_key` (all re-key copies) in one statement; independent sanctions on the same email keep their own roots. Re-key copies are only inserted while the root is active. Durations: permanent, 90 days default, or 3–6 calendar months in JST with end-of-month clamping (owner approval still required for the default).
* **Case claim.** The claim (`open` → `applying` with an operation id) is part of the same batch; it re-checks that the target exists, every evidence record still exists and belongs to the target, the evidence kinds, and (for linked cases) that the parent is still active, a shared-destination link exists and the target's own quarantined/unsafe link still exists. Retrying with the same `op` returns the original result; any other concurrent attempt gets 409. A unique index allows one UID sanction per case.
* **Parent reversal → hold → resolution.** Reversing the attacker's root puts dependent linked sanctions on **hold** (not enforced; `banned=2` is lifted by the sweep; Firebase sync is touched so a disabled account is re-enabled). Hold applies to every sanction made from a linked case, whatever `kind` it was applied with (including `temporary`). Resolution: `POST /api/admin/sanctions/:id/resolve` with `decision:"release"` (reverse; reason) or `decision:"reinstate"` (only if the case has `direct` evidence that still exists; reason ≥20 chars, `attest:true`, `confirm:true`). Time keeps running while held: a sanction that expired while held is **never** reinstated (409 `expired`, no visibility ban restored). Both touch Firebase sync, so no orphaned disabled account remains. Held rows are listed in the admin tab until resolved.
* **Email tombstones: reassignment and appeals.** A permanent email tombstone also blocks a future person who receives the same address. Sanctions never infer ownership beyond the verified-email match, and a historical/reassigned address is never automatically treated as the same person. Each email tombstone carries an immutable lineage id `elid` that groups the hashes of the **same address** across key versions (assigned when the verified email is first recorded; re-key copies inherit it; legacy rows get their own conservative lineage per row/parent chain). Round 5: when a verified email is recorded under a new key version, the lineage is inherited from any row **of the same UID** whose hash equals one of the hashes computed from the token's verified email under the keyring's versions — including legacy `lg:` lineages (only cryptographically matching hashes; different addresses never match, and another person who later receives the address has a different UID and gets a new lineage). If two or more distinct lineages match, the lexicographically smallest is used and the case is written to `elid_review` (admin tab, `health.ok=false`) for manual review — nothing is merged automatically. After an individual appeal, `POST /api/admin/sanctions/:id/release-email` — `:id` must be an email row — (reason ≥20, `reviewer`, `confirm:"RELEASE"`) releases only the rows of that root with that `elid`; other addresses in the same root, the UID sanction and other roots (overlapping sanctions on the same address) stay active. A re-key after release cannot resurrect it (copies are made only from active rows). Accounts that shared the email are touched for Firebase re-sync.
* **Appeals and rights while sanctioned.** The 403 message names the contact form (no sign-in needed). The contact form has kinds `appeal` and `account` (deletion / own-data requests); anyone can send them without signing in, the answer is identical whatever the handle (no account enumeration), and sending never lifts a restriction or deletes anything — staff verify ownership out of band (reply contact, and the verified email shown in the Firebase console) before acting. A sanctioned user with a working session can still `POST /api/contact` (kept with their UID) and `POST /api/me/delete` (sanction records remain; the UID↔email association is deleted). Limits: a Firebase-disabled user cannot obtain a token, so deletion goes through the request; the in-app Firebase account deletion may require a recent sign-in, and if it fails after the site data is deleted, the Firebase account remains (staff can remove it on request); manual bans (`banned=1`) keep the previous behaviour.
* **Expiry cadence (not a guarantee).** Writes by the sanctioned account re-check immediately. Public visibility (`banned=2`) is restored by the hourly cron (`0 * * * *`) and by periodic cleanup — expected within about 1 hour, but a failed run is only retried at the next run. Each run records success/failure in `job_runs` (shown in the admin tab). Manual bans (`banned=1`) are never touched.
* **In-flight requests (irreducible boundary).** The gate runs before every authenticated route. Note inserts (plain and link) re-check the sanction inside the same INSERT (UID, recorded emails, token email hashes), so a sanction created after the gate still blocks the post (403). Audited writes that rely on the gate decision taken at request start (no in-statement re-check): likes, reposts, bookmarks, follows/requests, DMs, profile/avatar/card updates, media upload, favourites/teams/memo sync, contact. A sanction created while one of these requests is already past the gate can let that single request complete; the next request is denied. No absolute guarantee of instant revocation is claimed.
* **Same verified identity.** A confirmed-attack sanction also hides (`banned=2`) other existing accounts that recorded the same verified-email hash; their sessions are denied by the gate and their Firebase sync is touched.
* **Key coverage and integrity.** On every authenticated request the gate checks that every key version used by active tombstones is in the ring and that each version's material matches its stored sentinel (`key_sentinels`: an HMAC of a fixed domain-separated string under that key — not the key, not usable to derive it). Before recording any verified-email hash, the current version's sentinel is verified (and recorded first if the version is new), so no hash is ever stored under unverified or mislabeled key material. Verified sentinels are memoised per D1 binding for at most 60 s, so a database restore or a changed sentinel is detected within 60 s on a warm isolate and immediately on a new one. Missing version, changed material under an existing version, or an unreadable ring ⇒ logged-in writes and `/api/me*` fail closed (503) when tombstones exist, hashes are not recorded, and the admin tab shows `missing_*_versions` / `mismatch_versions`. Hashes cannot be recomputed without the plaintext email, which is never stored — so **never remove or change a key version on elapsed time alone**. Recommended: keep one long-lived identity key (`v1`) and rotate only on suspected compromise; back up every version's material in the owner's secret manager together with the D1 backups it belongs to (restoring D1 with a different keyring fails closed); ring capacity is 32 versions.
* **Cost.** Measured in tests (steady state, sentinel memo warm): a logged-in GET adds 3 D1 queries over an anonymous one (1 pre-existing profile lookup + 2 for sanctions); a plain post uses 8 in total. The first authenticated request per D1 binding per 60 s adds the sentinel check (2 queries + 1 batch).

## 4. Rollback / kill switch
* **Stop new links**: unset `LINKS_POST`. Inline URLs are rejected by the legacy filter; an explicit `url` field is rejected, never silently dropped. Existing posts and `note_links` rows are kept.
* **Stop opening links**: unset `LINKS_CLICK`. Feeds immediately render links inert (`state:"off"`), and `open`/`go` refuse, including dialogs already open. Clients cache `/api/links/config` for up to 5 min, but the server is authoritative.
* **Never** delete `sanctions`, `sanction_events`, `sanction_cases`, `note_links`, `link_events` to roll back. Unsetting `SANCTIONS_ON` stops creating sanctions and recording hashes; it does **not** lift active sanctions.
* To lift one sanction: admin tab → 取り消す (reason + confirmation). The legacy `/api/admin/ban {on:false}` only lifts the manual ban; an active sanction keeps `banned=2`.
* Mixed versions: an old site ignores `ulink` and never sends `url`; a new site against an old Worker gets 404 for `/api/links/config` and hides the link UI. Tables and columns are additive (`CREATE … IF NOT EXISTS`, `ALTER … ADD COLUMN`).

### Data model
`notes.op` (per-request random key, unique when set; only link posts set it — the link row is attached by `op`, never by user+timestamp or `last_insert_rowid()`), `note_links` (+`rev`, `vh`), `link_intents`, `link_verdicts` (≤5000 clean rows; unsafe rows kept until provider expiry), `link_budget_d` (one row per UTC day; month = sum; the earlier one-row `link_budget` is unused), `link_leases`, `link_attempts`, `link_clicks`, `req_bad`, `link_events` (host + 16-hex hash prefix, no full URLs), `sanction_cases` (+`op`, `ek`, `lbasis`, `dsum`), `sanctions` (+`root_key`, `case_id`; status `active`/`held`/`reversed`/`released`; unique `(root_key, ehash)` for email rows, `(root_key)` and `(case_id)` for UID rows), `sanction_events` (+`root_key`), `user_emails`, `key_sentinels`, `fb_sync`, `job_runs`. `link_quota` is a legacy table from an earlier draft of this branch (still created and cleaned, never read or written by the budget). `users.banned`: 0 normal, 1 manual, 2 sanction-derived.

**利用ルール（案）**
- タイムラインの投稿・返信には、https:// で始まるリンクを1つだけ付けられます（確認済みのメールアドレスでログインした人だけ）。メッセージ・掲示板・対戦募集・プロフィールには、これまでどおりリンクは書けません。
- 短縮URL・転送するリンク・外部の連絡先（メッセージアプリ・招待など）・ログインの印や合言葉を含むリンクは付けられません。
- リンクは外部の安全確認サービスで確かめますが、問題が見つからなかったことは安全の保証ではありません。
- 意図的に危険なリンクを広めるなど、サイトや利用者への攻撃と運営が確かめた場合、そのアカウントは期限なく利用できなくなり、同じ確認済みメールアドレスでの再登録・利用もお断りします。関係すると確かめたアカウントは一定の期間（例：90日）利用を止めることがあります。通報・自動の判定だけでは止めません。異議は「お問い合わせ」から受け付けます。

**Rules (draft, EN)** — One https:// link per timeline post or reply (verified-email accounts only); links remain disallowed in messages, boards, the lobby and profiles. Shorteners, redirects, external-contact invites and URLs containing login tokens are refused. Links are checked by an external safety service; passing the check is not a guarantee of safety. Accounts confirmed by staff to have intentionally attacked the site or users are permanently barred, including re-registration with the same verified email; accounts confirmed as related may be restricted for a period (e.g. 90 days). Reports or automated verdicts alone never cause a sanction. Appeals via the contact form.

**プライバシーポリシー追記（案）** — リンクを付けた投稿では、そのリンク（#以降を除く）を Google Cloud Web Risk（Google LLC、米国）に送り、危険の可能性があるか確かめます。当サイトはリンク先のページを読みこみません。送ったリンクの Google 側での扱い（保存・利用・場所）は Web Risk の利用規約・データの取り扱いによります［公開前に契約・送り先・場所・安全管理を確かめて書く］。確認の結果は、問題が見つからなかったものは最長60分、危険の判定は Google が示す期限まで保存します。ログインは Google の Firebase Authentication で行い、利用停止の運用のため、ログインに使った確認済みメールアドレスを、鍵つきの一方向の変換（HMAC-SHA-256）をした値だけで保存します（メールアドレスそのものは保存しません）。アカウントを削除するとこの対応は消えますが、意図的な攻撃などで利用を止めた記録は、再登録を防ぐため［保存期間：下の案、要承認］保存します。異議・訂正・削除の相談は「お問い合わせ」（ログイン不要）で受け付けます。リンクの確認や利用停止の記録は匿名ではなく、運営者が確かめるためにアカウントと結びつけて保存します。

**Privacy (draft, EN)** — For posts with a link, the link (without the #fragment) is sent to Google Cloud Web Risk (Google LLC, United States) to check for known threats; we never fetch the page. How Google stores and uses submitted URLs, and where, is governed by the Web Risk terms [to be confirmed — contract, recipient, location and safeguards — before release]. "No match" results are kept up to 60 minutes; threat verdicts until the expiry given by Google. Sign-in uses Google Firebase Authentication; for moderation we store only a keyed one-way hash (HMAC-SHA-256) of your verified sign-in email, never the address itself. Deleting your account removes this association, but records of sanctions for confirmed intentional attacks are kept for [retention: see proposal below, pending approval] to prevent re-registration. Appeals, corrections and deletion requests: contact form (no sign-in needed). Link checks and sanction records are linked to the account (not anonymous) so staff can review them.

**Overseas transfer.** Japanese PPC guidance (https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/ and https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/, cited by the reviewer; not re-read from this environment) requires assessing the actual contract, recipient, country and safeguards before the text is published. **Owner/legal approval required; the live rules and privacy pages are unchanged.**

## 6. Firebase enforcement (code only — staging blocked)
Service-side denial (the gate) is authoritative and stays on even if Firebase sync or hooks are off. **Firebase has no distributed compare-and-set, and D1 and Firebase cannot share a transaction: exact atomicity is impossible and is not claimed.** The design converges Firebase to the D1 state, records enough *before* each external change that a crash, timeout or retry never loses ownership, and sends ambiguous cases to a human.
* **Desired state, not commands.** `fb_sync` has one row per UID. Any event that may change what Firebase should look like (sanction create — target and, for permanent sanctions, same-identity accounts —, reversal, hold, resolution, email release, expiry, manual ban/unban, admin replay/review) increments `gen` and keeps `pend_since` (when the row first became out of date; never refreshed by a claim). Desired state is computed from current D1 at claim time: `disabled` (an active sanction covers the UID), `review` (ownership ambiguous — never automatic), `hold` (ours, but a manual ban exists), `enabled` (ours, nothing restricts it now), `none` (not ours — never touched).
* **Protocol** (`FB_ADAPTER_TOKEN`): `GET /api/fb/env` (handshake: Worker `FB_ENV_ID` + project) → per account, just in time: `POST /api/fb/claim` leases **one** row for 60 s (the adapter passes the UIDs it already touched this run in `skip`) → read Firebase → `POST /api/fb/renew` (extends only while the same lease is held, unexpired and `gen` unchanged) → `POST /api/fb/intent` (records the observed state, `prior` and ownership **before** any external change; for enable it re-checks in the same statement that the row is ours, was not disabled before, is not under review and no sanction/manual ban exists) → renew → Firebase change (each SDK call bounded to 8 s) → renew → revoke → re-read → `POST /api/fb/ack`. `ack done` is accepted only with the current, unexpired lease and the claimed `gen` — checked inside the final UPDATE itself (`AND gen=?`); if `gen` moved, the ACK is turned into `superseded` (observation stored, not done). Metrics (`done`/`failed`/`unknown`/`superseded`) and `fb_sync_ok` are written in the same batch only when that UPDATE actually changed the row for this operation (`last_op` = lease) — a stale or zero-row ACK never counts as success. The adapter counts a non-200/409 ACK as `bad` (never done/noop; exit code 3), and its read after `superseded` is not treated as an unknown operation. Plus verified state (`observed_disabled`, `revoked` for disable). Expired, foreign or stale reports are never marked done; their observed state is stored (`obs_disabled`, `obs_at`, `obs_gen`, separate from desired state), ownership is kept, and the row is re-checked immediately. A repeated `done` after a lost response returns `repeat:true` (counted as `lost`). If `gen` changes while working, renew answers `superseded`; the adapter stops, acks `superseded` with the observed state (not a failure) and the same run re-claims and converges.
* **Unknown outcomes.** An SDK call that times out may still complete later (it cannot be cancelled). The adapter reports `failed` with `unknown:true` (row flag `unknown`, alert), never touches that UID again in the same run, waits up to 30 s for late calls to settle, re-reads the user and stores only the observation (`POST /api/fb/observe`, never "done"). Every unknown failure stores its lease token as `unk_op`; `/api/fb/observe` must carry that `op` and only an observation for the **current** unknown operation clears `unknown` or infers ownership — an observation for an older or overlapping operation is stored as observation only (`recorded_only:true`). If the late call settles, the observation also repairs ownership (a late *disable* that landed makes the row ours again, so a later reversal re-enables it) and bumps `gen` so the next run converges; calls that never settle leave `unknown=1` (alert) until an admin replays. The next run verifies and finishes. Residual: a hung call inside a process that is killed can complete at any later time; the daily re-check and the gate cover it.
* **Per-operation records (round 6, tightened in round 7).** Every external mutation has its own row in `fb_ops` (key = that run's lease token), **created in the same D1 transaction as the intent** (`/api/fb/intent`), before any Firebase call — a new lease is never associated with an older intent. Lifecycle: `pending` → resolved by any report carrying that lease (`done`, definite `failed`, `superseded`, or the same reports arriving after the lease expired: `late_*`), because a report means the adapter's call has returned; `failed` with `unknown:true` ⇒ `timeout`; lease no longer current with no report ⇒ `crash` (decided by the exact lease, no time heuristic). **Any unresolved row (pending/timeout/crash) blocks new claims for that UID**, so after a process death, a lost/rejected ACK or a timeout, nothing new is sent to Firebase for that account until it is resolved: by `/api/fb/observe` with that exact `op` (read-only re-read; resolution of the row and the ownership/review/generation update are **one D1 batch**, keyed by a per-request token, so a failure in between changes nothing and a retry is idempotent) or by `/api/admin/fb/replay` after staff checked the account in the Firebase console (manual reconciliation; `how='replay'`). The adapter reports how the late mutating call actually settled (`settled: ok|error|none`); ownership is inferred only when a *disable* settled `ok` and the account is observed disabled; observed disabled without a successful disable ⇒ `review` (`disabled_outside_unknown`). Duplicates are observation-only. Old records are migrated once (marker `link_state.fb_ops_mig`): `unknown=1`+`unk_op` ⇒ `timeout` with that op; a held lease with an intent (or `unknown` without op) ⇒ `legacy:<uid>` `crash`. The local gate remains authoritative while an account waits. Unavoidable: D1 and Firebase cannot share a transaction; a call sent by a process that dies can complete at any later time — that is exactly why the account is frozen until a human confirms.
* **Ambiguous ownership.** If an account was already disabled when first seen (`prior=1`, not ours), later re-enabled outside this system, and then disabled by this system, the row is marked `review` (`review_why=prior_disabled_then_enabled`) and is never re-enabled automatically. `POST /api/admin/fb/review {handle, decision:"enable"|"keep", reason ≥20, confirm:true}` (refused while leased). Known residual: a Firebase-console disable of an account this system already disabled cannot be detected at re-enable time — staff must use the site's manual ban (`banned=1`, blocks re-enabling).
* **Failures and alerts.** `failed` releases the lease and backs off (30 s doubling to 6 h); 10 failures ⇒ dead letter (never retried automatically). `POST /api/admin/fb/replay` is refused while a live lease exists. The admin sanctions API returns `fb_sync` with `backlog`, `dead`, `review`, `unknown`, `oldest_pending_since` (stable), `adapter_heartbeat_at` (any claim) vs `last_success_at` (last verified done), 7-day `metrics_7d` (`done`, `failed`, `unknown`, `stale`, `lost`, `superseded`), and `alert:true` for dead/review/unknown rows, anything pending >1 h, a backlog with no heartbeat for 2 h, or heartbeats without success for 2 h. The CLI exits 3 on dead or unknown rows.
* **Environments (default deny).** `tools/firebase-env.json` maps each environment to its own project, Worker URL, Worker `FB_ENV_ID` and service account; **every entry is `approved:false` and placeholders `<…>` are unset** — nothing runs until the owner fills and approves an entry. A non-production entry may not reuse any production value. The CLI needs `--live --env <name>`, `FB_ACTIVATE=<name>:<project>` (explicit activation), and a service-account key whose `project_id`/`client_email` match the entry; `runOnce` refuses a different SDK project or service account and a Worker whose `/api/fb/env` answer differs — all before any Firebase call. The blocking functions read the same map (`tools/firebase-blocking/firebase-env.json`, tested identical), take `FB_ENV`, refuse when `GCLOUD_PROJECT` differs, send only to that entry's Worker, and treat a check answer whose `env` differs as unreachable (fail policy). No production URL is hard-coded in either tool.
* **Adapter** `tools/firebase-adapter/` (`firebase-admin` 14.5.0, lockfile, `npm ci --ignore-scripts`; audit 0). Service account: least privilege (Firebase Authentication user management only). Revocation does not invalidate already-issued ID tokens immediately (up to 1 h); the gate covers that window.
* **Blocking functions** `tools/firebase-blocking/` (`firebase-functions` 7.4.0 + explicit `firebase-admin` 14.5.0, Node 22, lockfile; audit **0** — the previous 9 moderate `uuid` paths (GHSA-w5hq-g745-h8pq via firebase-functions 6.1.0 → firebase-admin 12.7.0 → Google Cloud libraries) are gone; 7.4.0's peer range accepts firebase-admin 14 and its GraphQL/Apollo peers are optional). `beforeUserCreated` / `beforeUserSignedIn`: `AbortSignal` timeout (2 s) with the timer always cleared, circuit breaker (5 failures ⇒ 30 s), only the UID and a **verified** email are sent, neutral message, no logging. `tests/fb-sdk.mjs` loads the real SDK, checks both triggers register (`providers/cloud.auth/eventTypes/user.beforeCreate|beforeSignIn`, secret `FB_HOOK_TOKEN`) and runs them via `run(event)` against stubbed fetch (default map ⇒ deny without network; approved map ⇒ only that Worker; wrong project or wrong answer env ⇒ deny). Requires the Identity Platform upgrade (cost) — **owner approval required; not deployed**; optional only if the owner changes the original Firebase-side sign-up-blocking requirement. Emulator/real staging: **not run**.

## Monitoring and incident response (proposal)
* Alert on: `job_runs.sanction_sweep` failures, key `health.ok=false` (missing/mismatched versions), Web Risk errors/budget near cap (`budget` in the links tab), `fb_sync.alert`, dead letters.

* Outages: new and expired link checks fail closed; plain posts and anonymous tools keep working; local sanctions stay authoritative.
