# Secure link posting — configuration, rollback and policy drafts

Status: implemented on `feature/secure-link-posting`, **all flags OFF by default, not released**. Do not enable in production until every gate in `docs/secure-link-posting-report.md` §7 is closed.

## 1. Server flags and secrets (Cloudflare Worker settings — names only)

| Name | Kind | Default | Effect |
|---|---|---|---|
| `LINKS_POST` | variable | unset (OFF) | `1` = authenticated timeline notes/replies may carry one HTTPS link. Also requires `SANCTIONS_ON=1`, a valid email keyring with a current version, and `WEBRISK_API_KEY`; otherwise link posts are refused (503) and plain posts are unaffected. |
| `LINKS_CLICK` | variable | unset (OFF) | `1` = links can be opened through the two-step `open` → `go` flow. OFF = feeds return `state:"off"` (host only) and both endpoints return 403 `inert`. |
| `SANCTIONS_ON` | variable | unset (OFF) | `1` = admins can create case records and sanctions; verified-email hashes start being recorded. **Active sanctions are enforced regardless of this flag.** |
| `WEBRISK_API_KEY` | secret | unset | Google Cloud Web Risk key, sent only in the `x-goog-api-key` header to the fixed endpoint `https://webrisk.googleapis.com/v1/uris:search`. Never returned or logged. |
| `EMAIL_HMAC_KEYRING` | secret | unset | JSON `{"<version>":"<key ≥32 chars>", …}` (≤32 versions, version = `[A-Za-z0-9_-]{1,16}`). **All versions still referenced must stay in the ring, and a version's key material must never change** (checked against `key_sentinels`). |
| `EMAIL_HMAC_KEY_CURRENT` | variable | — | Version used for new hashes. Must exist in the ring, or the ring is treated as invalid. |
| `EMAIL_HMAC_KEY` / `_VER`, `EMAIL_HMAC_KEY_PREV` / `_PREV_VER` | secret / variable | unset / `v1` / `v0` | Legacy single-key form; merged into the ring (`EMAIL_HMAC_KEY` is current unless `EMAIL_HMAC_KEY_CURRENT` says otherwise). |
| `LINKS_WEBRISK_DAY` | variable | `3000` | Global daily cap on provider calls (UTC day). |
| `LINKS_WEBRISK_MONTH` | variable | `90000` | Global monthly cap (UTC calendar month). Day and month are reserved together in one single-row `UPDATE … RETURNING` (`link_budget`), only after a lease is held; admitted calls count even if they fail; cache hits never count. |
| `LINKS_WEBRISK_CONC` | variable | `4` | Global concurrent provider calls (1–16), enforced by D1 lease rows shared by every isolate. |
| `LINKS_WEBRISK_MS` | variable | `3000` | Provider timeout (500–5000 ms). A lease expires at timeout + 2 s, so a crashed isolate's lease is recovered automatically. |
| `LINKS_CLEAN_TTL_MIN` | variable | `30` | Local lifetime of a "no match" verdict (5–60 min) — a site policy, not a provider guarantee. Unsafe verdicts are kept exactly until the provider's `expireTime` (no cap, and a forced fresh lookup never shortens them); a missing/invalid `expireTime` is treated as malformed (fail closed, not cached); a past `expireTime` denies the current operation without caching. |
| `FB_ADAPTER_TOKEN` | secret | unset | ≥32 chars. Lets `tools/firebase-adapter` use `/api/fb/claim`, `/api/fb/intent`, `/api/fb/ack`. Separate from `ADMIN_TOKEN`. Unset ⇒ endpoints return 404. |
| `FB_HOOK_TOKEN` | secret | unset | ≥32 chars. Lets the blocking functions call `/api/fb/check` (answer is `{deny}` only). Unset ⇒ 404. |

No new binding is required; all new tables live in the existing D1 (`DB`).

## 2. Enabling (only after the release gates)
1. Create the keyring as a secret (`EMAIL_HMAC_KEYRING`, random keys ≥32 chars) and set `EMAIL_HMAC_KEY_CURRENT`. Set `WEBRISK_API_KEY`.
2. `SANCTIONS_ON=1` first and check the admin tab「リンク・利用停止の記録」: the key-status banner must be absent (`health.ok`).
3. `LINKS_CLICK=1`, then `LINKS_POST=1`. `GET /api/links/config` must return `{"post":true,"click":true}`.
4. Apply the approved rules/privacy text (§5) in the same release.

## 3. Behaviour that operators must know
* **Opening a link (two steps).** Feeds return only `{host, state}` (`ok` | `off` | `blocked`), never the full URL. `POST /api/links/:id/open` re-checks visibility, state and a fresh verdict (re-reading them after any asynchronous re-check) and returns the URL for the confirmation dialog plus a one-use intent valid 60 s and bound to the viewer and the link's revision. `POST /api/links/:id/go` consumes the intent atomically and re-checks visibility, state, revision, verdict expiry and the flag before returning the URL. The browser opens a blank tab inside the click, clears `opener`, and navigates it through a `no-referrer` meta refresh only after `go` succeeds; on any refusal the tab is closed. If the browser blocks the tab, **no `<a href>` is ever rendered**: a 「もう一度開く」 button appears for 30 s; pressing it opens a blank tab inside that click and repeats `open` (new intent) → `go`, so a link quarantined in between is refused. If tabs are still blocked, the user is asked to copy the address already shown in the dialog.
* **Limits that cannot be removed:** a URL already shown in a dialog (or copied) cannot be revoked from the user's memory; there is an unavoidable race between the final `go` answer and the external navigation; a destination can change after it was checked. "No match" is never presented as "safe".
* **State changes are revision-guarded.** Every state change on `note_links` increments `rev`. Re-checks (click, report) and admin restore/recheck write only if `rev` is unchanged since they read it; admin quarantine always wins and increments `rev`, invalidating outstanding intents.
* **Provider budget and shared verdicts.** Shared cache (key = policy version + canonical URL without fragment) → lease (global, D1) → day+month budget → fetch → release. Every publish, `open` and `go` consults the shared verdict, so an unsafe answer for the same destination found through another post makes this post inert before its own TTL; `go` reads the consumed intent, the post's visibility, the link row and the shared verdict in one D1 batch (one transaction) at response time. Eviction only removes expired rows and old clean rows; unexpired unsafe rows are never evicted. A cache read/write failure fails closed for links only.
* **Request bounds.** JSON bodies are read as a stream and cancelled at 256 KB (with or without `Content-Length`); only JSON objects are accepted. Malformed bodies count per client (salted IP hash): 30 per 10 min per client, 5000 per 10 min globally, then 429. Link intents (field present or `http(s)://` in text) take the per-UID slot (10 s / 12 per h / 40 per day) before any other check, including malformed ones. Every note insert enforces 15 s / 100 per day inside the INSERT itself, so concurrent plain and link posts cannot exceed it.
* **Case records (evidence).** `POST /api/admin/cases` requires: target, kind `attack`|`linked`, summary ≥20 chars, 1–10 references to this site's own records that belong to the target (note, link, link_event, report — never IP/device), `attest:true` (the reviewer personally checked the evidence) and `evidence_kinds` containing `direct` (the target's own wrongdoing). A **linked** case additionally requires `linkage` in `evidence_kinds`, `linkage_basis` ∈ `self_admitted` / `evasion_after_sanction` / `coordinated_reviewed`, a `direct_summary` ≥20 chars of what the target personally did, an active confirmed-attack parent root, a target link with the same destination as a link in the parent's case, **and** a target link that staff quarantined or that was judged unsafe. `shared_url`, `ip`, `device`, `report` and `scanner` are explicitly rejected as linkage bases: a shared destination (e.g. someone reposting a guide), IP, device, reports or a scanner verdict alone never makes a linked case (no guilt by association). Evidence kinds and basis are stored on the case (`ek`, `lbasis`, `dsum`).
* **Sanctions.** `POST /api/admin/sanctions` needs the open case, rationale ≥20 chars and `confirm:"SANCTION"`. **Permanent** (`perpetrator`) additionally needs `basis` = `deliberate_attack` or `proven_evasion` (recorded in `evidence` as `case:N|basis`); an unsafe verdict alone is never a basis. The UID row, email tombstones, audit events, `banned=2`, the Firebase sync touch and the case status are written in one D1 batch under one immutable `root_key`. Reversal reverses every row with that `root_key` (all re-key copies) in one statement; independent sanctions on the same email keep their own roots. Re-key copies are only inserted while the root is active. Durations: permanent, 90 days default, or 3–6 calendar months in JST with end-of-month clamping (owner approval still required for the default).
* **Case claim.** The claim (`open` → `applying` with an operation id) is part of the same batch; it re-checks that the target exists, every evidence record still exists and belongs to the target, the evidence kinds, and (for linked cases) that the parent is still active, a shared-destination link exists and the target's own quarantined/unsafe link still exists. Retrying with the same `op` returns the original result; any other concurrent attempt gets 409. A unique index allows one UID sanction per case.
* **Parent reversal → hold → resolution.** Reversing the attacker's root puts dependent linked sanctions on **hold** (not enforced; `banned=2` is lifted by the sweep; Firebase sync is touched so a disabled account is re-enabled). Resolution: `POST /api/admin/sanctions/:id/resolve` with `decision:"release"` (reverse; reason) or `decision:"reinstate"` (only if the case has `direct` evidence that still exists; reason ≥20 chars, `attest:true`, `confirm:true`). Both touch Firebase sync, so no orphaned disabled account remains. Held rows are listed in the admin tab until resolved.
* **Email tombstones: reassignment and appeals.** A permanent email tombstone also blocks a future person who receives the same address. Sanctions never infer ownership beyond the verified-email match, and a historical/reassigned address is never automatically treated as the same person. After an individual appeal, `POST /api/admin/sanctions/:id/release-email` (reason ≥20 chars, `confirm:"RELEASE"`) sets that root's email rows to `released`; the confirmed attacker's UID sanction and any other root's tombstones stay. Accounts that shared the email are touched for Firebase re-sync.
* **Appeals and rights while sanctioned.** The 403 message names the contact form (no sign-in needed). A sanctioned user can still `POST /api/contact` (kept with their UID so the appeal can be matched) and `POST /api/me/delete` (sanction records remain; the UID↔email association is deleted). Manual bans (`banned=1`) keep the previous behaviour (deletion via contact).
* **Expiry cadence (not a guarantee).** Writes by the sanctioned account re-check immediately. Public visibility (`banned=2`) is restored by the hourly cron (`0 * * * *`) and by periodic cleanup — expected within about 1 hour, but a failed run is only retried at the next run. Each run records success/failure in `job_runs` (shown in the admin tab). Manual bans (`banned=1`) are never touched.
* **In-flight requests (irreducible boundary).** The gate runs before every authenticated route. Note inserts (plain and link) re-check the sanction inside the same INSERT (UID, recorded emails, token email hashes), so a sanction created after the gate still blocks the post (403). Audited writes that rely on the gate decision taken at request start (no in-statement re-check): likes, reposts, bookmarks, follows/requests, DMs, profile/avatar/card updates, media upload, favourites/teams/memo sync, contact. A sanction created while one of these requests is already past the gate can let that single request complete; the next request is denied. No absolute guarantee of instant revocation is claimed.
* **Same verified identity.** A confirmed-attack sanction also hides (`banned=2`) other existing accounts that recorded the same verified-email hash; their sessions are denied by the gate and their Firebase sync is touched.
* **Key coverage and integrity.** On every authenticated request the gate checks that every key version used by active tombstones is in the ring and that each version's material matches its stored sentinel (`key_sentinels`: an HMAC of a fixed domain-separated string under that key — not the key, not usable to derive it). Before recording any verified-email hash, the current version's sentinel is verified (and recorded first if the version is new), so no hash is ever stored under unverified or mislabeled key material. Verified sentinels are memoised per D1 binding for at most 60 s, so a database restore or a changed sentinel is detected within 60 s on a warm isolate and immediately on a new one. Missing version, changed material under an existing version, or an unreadable ring ⇒ logged-in writes and `/api/me*` fail closed (503) when tombstones exist, hashes are not recorded, and the admin tab shows `missing_*_versions` / `mismatch_versions`. Hashes cannot be recomputed without the plaintext email, which is never stored — so **never remove or change a key version on elapsed time alone**. Recommended: keep one long-lived identity key (`v1`) and rotate only on suspected compromise; back up every version's material in the owner's secret manager together with the D1 backups it belongs to (restoring D1 with a different keyring fails closed); ring capacity is 32 versions.
* **Cost.** Measured in tests (steady state, sentinel memo warm): a logged-in GET adds 3 D1 queries over an anonymous one (1 pre-existing profile lookup + 2 for sanctions); a plain post uses 8 in total. The first authenticated request per D1 binding per 60 s adds the sentinel check (2 queries + 1 batch).

## 4. Rollback / kill switch
* **Stop new links**: unset `LINKS_POST`. Inline URLs are rejected by the legacy filter; an explicit `url` field is rejected, never silently dropped. Existing posts and `note_links` rows are kept.
* **Stop opening links**: unset `LINKS_CLICK`. Feeds immediately render links inert (`state:"off"`), and `open`/`go` refuse, including dialogs already open. Clients cache `/api/links/config` for up to 5 min, but the server is authoritative.
* **Never** delete `sanctions`, `sanction_events`, `sanction_cases`, `note_links`, `link_events` to roll back. Unsetting `SANCTIONS_ON` stops creating sanctions and recording hashes; it does **not** lift active sanctions.
* To lift one sanction: admin tab → 取り消す (reason + confirmation). The legacy `/api/admin/ban {on:false}` only lifts the manual ban; an active sanction keeps `banned=2`.
* Mixed versions: an old site ignores `ulink` and never sends `url`; a new site against an old Worker gets 404 for `/api/links/config` and hides the link UI. Tables and columns are additive (`CREATE … IF NOT EXISTS`, `ALTER … ADD COLUMN`).

### Data model
`notes.op` (per-request random key, unique when set; only link posts set it — the link row is attached by `op`, never by user+timestamp or `last_insert_rowid()`), `note_links` (+`rev`, `vh`), `link_intents`, `link_verdicts` (≤5000 clean rows; unsafe rows kept until provider expiry), `link_budget` (one row: UTC day + month counters), `link_leases`, `link_attempts`, `link_clicks`, `req_bad`, `link_events` (host + 16-hex hash prefix, no full URLs), `sanction_cases` (+`op`, `ek`, `lbasis`, `dsum`), `sanctions` (+`root_key`, `case_id`; status `active`/`held`/`reversed`/`released`; unique `(root_key, ehash)` for email rows, `(root_key)` and `(case_id)` for UID rows), `sanction_events` (+`root_key`), `user_emails`, `key_sentinels`, `fb_sync`, `job_runs`. `link_quota` is a legacy table from an earlier draft of this branch (still created and cleaned, never read or written by the budget). `users.banned`: 0 normal, 1 manual, 2 sanction-derived.

## 6. Firebase enforcement (code only — staging blocked)
Service-side denial (the gate) is authoritative and stays on even if Firebase sync or hooks are off. D1 and Firebase cannot be one transaction; the design keeps Firebase converging to the D1 state and records enough before each external change that a crash or retry never loses ownership.
* **Desired state, not commands.** `fb_sync` has one row per UID. Any event that may change what Firebase should look like (sanction create — target and, for permanent sanctions, same-identity accounts —, reversal, hold, resolution, email release, expiry, manual ban/unban, admin replay) increments `gen`. The adapter's work is always derived from current D1 state at claim time: `disabled` (an active sanction covers the UID), `hold` (this system disabled it but a manual ban exists — do not re-enable), `enabled` (this system disabled it and nothing restricts it now), `none` (not ours — never touched).
* **Protocol** (`FB_ADAPTER_TOKEN`): `POST /api/fb/claim` leases up to 20 due rows for 90 s with a random lease token (one runner per UID; a second runner gets nothing; changed rows first, then a daily re-check of every row). Before any external change the adapter calls `POST /api/fb/intent` with the observed Firebase state: for `disable` the Worker records `prior` (was it already disabled?) and takes ownership only if it was not — a retry after a partial failure never overwrites the first observation, so ownership is never lost; for `enable` the Worker re-checks in the same statement that the row is ours, was not disabled before, and that no active sanction or manual ban exists right now (else 409, nothing is enabled). The adapter then changes Firebase, revokes refresh tokens (disable), re-reads the user to verify, and calls `POST /api/fb/ack`. `ack` is accepted only with the current lease token and the claimed `gen`; a `done` for `disabled` requires `observed_disabled:true` and `revoked:true`. A repeated `done` after a lost response returns `repeat:true`; any other stale report gets 409. If `gen` advanced meanwhile (e.g. reversal while disabling), the row stays due and the next run converges (residual window: one run).
* **Failures.** `failed` releases the lease and schedules a retry with backoff (30 s doubling to 6 h). After 10 failures the row is **dead-lettered** (`dead=1`, never retried automatically); the admin sanctions API shows `fb_sync` (`backlog`, `dead`, `oldest_pending_at`, `adapter_last_at`) with `alert:true` when there is a dead letter, something pending for over 1 h, or a backlog while the adapter has not run for 2 h, and lists dead rows (`fb_dead`). **Controlled replay:** `POST /api/admin/fb/replay {handle, reason, confirm:true}` (admin only, logged) resets the row and bumps `gen`. Crashes: an unacknowledged lease expires after 90 s and the row is re-claimed. Firebase SDK calls and Worker calls are bounded (8 s; Worker fetches use `AbortSignal` and `redirect:"error"`). The CLI exits with code 3 when dead letters remain so an external scheduler/monitor can alert.
* **Adapter** `tools/firebase-adapter/` (Node ≥20, `firebase-admin` 14.5.0 pinned with `package-lock.json`, install with `npm ci`; `npm audit`: 0): runs only with `--live`, an approved `FB_PROJECT_ID` that must equal the SDK's project, and `FB_ADAPTER_API` equal to the allowlisted HTTPS endpoint `https://pokechan-tap.pokechan.workers.dev` (`API_ALLOW`). Service account: least privilege (Firebase Authentication user management only). Revocation does not invalidate already-issued ID tokens immediately (up to their 1 h lifetime); the gate covers that window. Known limit: if staff disable an account by hand in the Firebase console while this system also owns its disable, re-enabling cannot tell the difference — use the site's manual ban (`banned=1`), which blocks re-enabling.
* **Blocking functions** `tools/firebase-blocking/` (`beforeUserCreated` / `beforeUserSignedIn`, Cloud Functions v2, `firebase-functions` 6.1.0 unchanged and now locked with `package-lock.json`): fixed destination `https://pokechan-tap.pokechan.workers.dev/api/fb/check` (not configurable), `redirect:"error"`, 2 s timeout that aborts the fetch through `AbortSignal` and always clears its timer, circuit breaker (5 consecutive failures ⇒ 30 s without calling the Worker, answering with `FB_HOOK_ON_ERROR`, default `deny`). Sends only the UID, and the email only when it is verified. Neutral user message; the answer contains only `{deny}`; nothing is logged. An unverified email is never treated as proof of ownership, so absolute sign-up prevention cannot be guaranteed across providers. Requires the Identity Platform upgrade (cost) — **owner approval required; not deployed** (optional only if the owner explicitly changes the original Firebase-side sign-up-blocking requirement). Rollback: delete the two functions; the gate keeps enforcing. `npm audit` reports 9 **moderate** advisories, all from `uuid <11.1.1` (GHSA-w5hq-g745-h8pq, missing buffer bounds check when a `buf` argument is passed) inside Google Cloud client libraries pulled in through `firebase-admin` 12; the hook code never calls `uuid`. The only fix is a `firebase-functions` major upgrade (7.x) — not done (no arbitrary upgrade); decide before any deployment.
* **Validation status:** mock tests (`tests/fb-adapter.mjs`, 102 assertions: crash, lost ACK, partial revoke, two runners, stale disable after reversal, new ban before enable, overlapping roots, expiry, manual ban/unban, dead letter/replay, timeouts, daily re-check, project/endpoint allowlist, hook abort/breaker) and the Worker side on real local D1 (`tests/d1-integration.mjs`). Emulator and dedicated staging project tests are **blocked** (no approved project/credentials in this environment).

## Monitoring and incident response (proposal)
* Alert on: `job_runs.sanction_sweep` failures, key `health.ok=false` (missing/mismatched versions), Web Risk errors/budget near cap (`budget` in the links tab), `fb_sync.alert`, dead letters.
* Incident: unset `LINKS_POST` and `LINKS_CLICK` first. **Never** lift active sanctions by toggling `SANCTIONS_ON` (it does not lift them). Roll back forward-compatibly; never delete evidence tables or the D1 database.
* Outages: new and expired link checks fail closed; plain posts and anonymous tools keep working; local sanctions stay authoritative.

## 7. D1 validation
* **Local, official runtime:** `tests/d1-integration.mjs` runs the built Worker in workerd via Miniflare `4.20260730.0` (pinned devDependency) with a disposable in-memory D1 and all outbound calls answered locally.
