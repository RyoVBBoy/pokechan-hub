## 1. 実装順と公開条件

- B1 は「今おすすめのパーティを教えて」→ 必要なら形式を確認 → 候補と理由 →「このポケモンは残したい」を引き継ぐ、までを一つの会話として実装。
- 続いて B2 は「なんか勝てなくなった」からパーティを任意で共有し、強み・選出・次に試すことを最大2件。B3 は「最新情報」から公式更新やレギュレーションの確認済み事項を回答。公式更新と利用者の対戦観測は別に表示。
- B1のコードとモック通信試験は開始可能。Stage Aの役割逆転修正を取り込み、固定評価・実機確認を引き継ぐ。B1初期はダメージ相談を既存入口に案内し、自由文の攻防判定から数字を生成しない。Stage Aの独立レビュー残件は `ガブリアスがカイリューにいわなだれを使ったら何発で倒れる？` と `当てたら` など。
- 本番提供、外部APIへの実際のリクエスト、契約、有料化は別途承認。各機能は既定無効とし、模擬通信・テスト用環境で先に完成させる。広告はこの段階の範囲外。mainと既存の公開・監査作業への統合は行わない。

## 2. B1のユーザー体験

1. `今おすすめのパーティ教えて` で、形式によって候補が変わり未指定ならシングル／ダブルを会話内で確認する。すでに指定済みなら聞き直さない。
2. 確認済みの候補を最大3件。候補ごとに6匹、向く戦い方、理由を最大2件、条件、適用版、検証状況、集計期間またはシーズンと出典を示す。`一番勝てる` などの保証や、確認のない現在の強さ順位は付けない。
3. `さっきの案でメガリザードンは残したい`、`2つ目をサイクル寄りに` を受付。候補番号を内部の候補IDへ紐付け、残す条件を維持。メガリザードンX／Yの違いが提案に影響する場合だけ確認する。厳密条件に一致するものがなければ、条件を勝手に緩めず、他の条件の変更か既存構築ツールへの導線を表示。
4. 現行レギュレーションを確認できない、対象レギュレーションの候補が古い、対象の合法性に根拠がない場合は `今おすすめ` を断定しない。表示できる過去の候補には過去のシーズンと未確認箇所を明示。
5. 無料は現行既定の1日5回答・月30回答。確認のみ、保留、失敗は回答枠を消費しない。複数カードを返しても1ターンにつき1回答。API費用は実際に送った呼び出しとして別に記録。上限ではリセット時刻と既存の無料ツールへの導線を表示し、入力済みの質問は同一セッションの下書きに残す。

## 4. 生成AIと会話状態

- Stage Aの `Provider` とゲーム別アダプターを拡張し、1社目の実プロバイダーアダプターはOpenAIの構造化出力を候補とする。モデルID・料金表・プロンプト版をサーバー設定で固定。正規化された結果を同じ契約で返すモックと、固定HTTPS宛ての実アダプターを分ける。実アダプターの試験はHTTPをモックし、実API呼び出しは承認済みの検証環境でのみ行う。
- 第1段は自由文から `intent`、形式候補、必須条件、選択候補、確認が必要なフィールドを列挙型とIDで抽出。既知の会話状態と照合し、ユーザーが明示した修正だけを反映。別ゲーム・別形式・別版の状態を流用しない。検索と計算の起動はサーバーの許可済み処理のみ。
- 第2段は必要な場合だけ、抽出済み候補から回答の順序・観点を生成。モデル出力は候補ID、理由ID、確認項目、テンプレートID。全てのIDと組合せを再検証し、種族・技・数値・日付・出典URLは取得した根拠からカードに挿入する。勝率・順位・仕様を生成した自由文として表示しない。形式不正・拒否・出力の途切れ・未知IDは安全な確認／保留へ。
- 会話は認証済みUIDとゲーム・形式・版に紐付く短命な構造化状態（最大6ターン、初期30分）。実装はサーバー署名付き状態または期限付き状態キーを選択。生の履歴を全件送らない。署名検証と所有者照合、アカウント切替・ログアウト・退会時の画面クリアと遅延応答破棄、サーバー側での期限と削除、同一ターンの冪等性を試験する。古い候補を引用した場合はデータを更新して再評価。
- AIに送る前に個人情報の送信を減らす。ID・ログイン情報・DM・他者データはモデル入力から除外。自由文の外部送信は用途・保持条件を明示し、適用される未成年者対策・データ保持／処理地域・契約を審査した後に有効化する。`store:false` と提供元の保持条件は別に確認。鍵はWorkerシークレット、本文はログに残さない。
- 最大2呼び出し。各呼び出し前に、適用単価と最大課金トークンで費用を予約し、全体予算に達したら停止。通信結果が不明なら最大見積額を保持。生の超過使用量を切り捨てず異常として記録し停止。リトライは初期無効。既存の手動停止と予算に加え、異常率・費用急増時に新規推論を止める仕組みを実利用前に検証。メトリクスは回数・トークン・費用・待ち時間・理由と版のみ。

## 5. 受け入れ

- Stage Aの固定230件を維持。B1用に新規60件以上（曖昧な短文12、複合条件12、会話の続き12、鮮度・出典・合法性12、分離・失敗・利用枠12）。独立に作った期待値を固定し、回答の対象と条件、候補・根拠、確認すべき点、保留、枠の消費を採点する。
- 重大誤答、根拠捏造、条件の取り違え、非公開データの表示、ゲーム・版・形式の混同、二重消費は0件。回答可能な事例は95%以上。人手レビューで戦い方に沿った理由・次の行動の妥当性を別に記録。実API承認後は同一ケースで複数回試す。P95 8秒以内を目標に通信と処理を別計測。
- 基準ケース `今オススメのパーティ教えて` → ダブル → `2つ目で、メガリザードンYは残したい`、現行データなし、非公開の強い候補、版変更、切替直後の応答、停止中、月末の枠。確認のターンでは消費せず、候補や助言が実際に返ったターンでだけ1回消費することを確認。
- ビルド、既存回帰、AI固定評価、D1並列、モバイル／PCブラウザーを実行し、SHA・差分・ケースとアサーションの数・残件を記録する。

- 実装時は [フェアプレイ仕様](./stage-b-fair-play-spec.md) を適用する。[独立評価データ](../../tests/ai-eval/stage-b1-acceptance.json) の通常60件とフェアプレイ28件を、固定の期待値を維持して実装のテストランナーへ接続する。複数ターンは順に同一の会話へ送り、mode・phase・kind は採点用ラベルとしてテスト入力に渡さない。未実装の後続機能は安全な案内の動作を判定する。
